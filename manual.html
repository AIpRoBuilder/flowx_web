01 / REQUIREMENTS

What you need

  • Python 3.10 or later.
  • Git, to obtain FlowX and its workflow runtime dependency.
  • An MCP-capable coding agent, or your own Python or A2A agent, to write the artifacts FlowX asks for.

FlowX does not call a model. It hands your agent a contract for each artifact, audits and tests what comes back, publishes versioned nodes, renders the FastAPI service, and runs it.

No keys required: provider and media variables are only needed by the workflows you generate when those workflows call a model or media service. Put them in the process environment or in the workflow service's own .env.

02 / INSTALL

Clone and install

One installation includes the shared core, the MCP server, the Python SDK, and the A2A adapter.

bash
git clone https://github.com/AIpRoBuilder/FlowX.git
cd FlowX
python3.10 -m venv .venv
source .venv/bin/activate
python -m pip install --upgrade pip
python -m pip install -e .

Poetry, uv, and conda are also documented. With Poetry: poetry env use python3.10 and poetry install. With uv: uv sync. With conda: conda env create -f environment.yml.

03 / CONFIGURE

Point FlowX at a workspace

Copy the example environment file and set the workspace where workflows and artifacts will live.

.env
cp .env.example .env

# .env
FLOWX_DEFAULT_WORKSPACE=./.flowx_workspaces

FLOWX_CONFIG_ROOT lets an installed flowx-mcp resolve a .env file outside the repository checkout. FLOWX_EXTRA_PATHS can point at a local ag_ui_workflow source when it is not installed into the current environment.

The SDK and A2A server read process environment variables; they do not automatically load this .env file. Export the settings or load the file in your application before creating a client: set -a; source .env; set +a.

04 / MCP

Register the local server

Check the entry point, then register the absolute path to your virtual environment's flowx-mcp in your MCP client.

bash
flowx-mcp            # local stdio entry point
flowx-mcp --verbose  # verbose logging
python3.10 run_server.py  # source-checkout entry point
mcp.json
{
  "mcpServers": {
    "flowx": {
      "command": "/absolute/path/to/your/venv/bin/flowx-mcp",
      "env": {
        "FLOWX_DEFAULT_WORKSPACE": "/absolute/path/to/flowx_workspaces"
      }
    }
  }
}

MCP hosts may not inherit your shell's PATH. Use absolute paths and store workflow credentials according to your client's security guidance.

05 / AGENT SKILL

Teach the host to use the loop

The FlowX skill guides a compatible coding agent through building, inspecting, repairing, running, and evolving workflows. Installing the skill copies its instructions and scripts, not the SDK; registering MCP is a separate step.

Claude Code

npx skills add AIpRoBuilder/FlowX --skill flowx-workflows -a claude-code -g

Codex

npx skills add AIpRoBuilder/FlowX --skill flowx-workflows -a codex -g

Hermes Agent

hermes skills install AIpRoBuilder/FlowX/skills/flowx-workflows

VS Code / Copilot

mkdir -p ~/.copilot/skills/flowx-workflows then copy skills/flowx-workflows/. into it.

DeepSeek Harness also has a read-only viewer plugin, installed separately with dsh plugin --profile web add ./plugins/deepseek-harness-flowx from a FlowX checkout. Use the skill to build, evolve, and run workflows.

06 / FIRST BUILD

Describe, submit, inspect

After setup, ask your MCP-capable agent to build something specific. FlowX allocates the workflow, returns contract packets, and gates every artifact.

PROMPT
Use flowx to build a workflow.

Build a workflow that accepts a support ticket, classifies its
category, assigns a priority, and drafts a reply. Name the reply
node draft_reply. Return the category, priority, and draft reply
as structured output.

What happens next

  • create_workflow allocates the folder and workflow_id.
  • begin_build opens a revision and returns next_tasks with the contract for each artifact.
  • The agent submits the requirement, the graph, then one code and test pair per node.
  • Rejections include findings with rule, line, remediation, and a repair task; max_attempts is bounded.
  • get_build_state and get_build_events show stages, node status, the next action, and the journal.

Build state lives in the MCP server process and in build/events.jsonl. After a restart, call begin_build again: published nodes are reused, so only unfinished work is requested.

07 / PYTHON SDK

Embed the builder

Use the SDK when your own Python agent or application backend should answer the contracts without an MCP transport.

python
from flowx_sdk import FlowXClient

def solve(task: dict) -> dict:
    # contract, context, meta, and submit.slots say what to write.
    return my_agent.write(task)

with FlowXClient(workspace="./workflows") as flowx:
    workflow_id = flowx.create_workflow("ticket-triage")
    state = flowx.build(workflow_id, "Categorize support tickets.", solve)
    assert state["status"] == "completed", state["errors"]
    print(flowx.run_service(workflow_id))
    input("Press Enter to stop the service... ")

Keep the client open while using the service; exiting the with block stops services it started and aborts open builds, while published versions stay. For finer control, call begin_build, get_tasks, submit_task, get_build_state, get_build_events, reopen_stage, and abort_build directly.

08 / A2A

Let another agent delegate

Start the non-streaming A2A adapter and point a peer agent at it. A build is an A2A task; while contract tasks are open, the task is input-required.

bash
flowx-a2a --host 127.0.0.1 --port 8001

The agent card is served at /.well-known/agent-card.json and JSON-RPC at /a2a. Supported methods are message/send, tasks/get, and tasks/cancel.

09 / ARCHITECTURE

Two entities, three interfaces

flowx_core.builder (WorkflowBuilder) sends contracts, verifies what comes back with auditors and pytest, publishes versions, and renders the service. flowx_core.service (ServiceManager) runs and drives the result. flowx_mcp, flowx_sdk, and flowx_a2a expose both to different agent hosts.

packages/a2a    flowx_a2a    non-streaming adapter

10 / GUARDRAILS

Review before you run

  • Submitted node tests run locally under pytest, and a smoke test or service run executes generated code. Review the artifacts and code before running the service.
  • Generated code and tests are not sandboxed. Provider calls can be billable.
  • Workflow files are FlowX-owned. Inspect them with read_workflow_artifact; change them with begin_build or begin_evolve. verify_workflow checks recorded SHA-256 digests.
  • Keep credentials in the process environment or the workflow service's own .env; never commit them to a repository.
Need the full protocol? Read DYNAMIC_WORKFLOW.md for builder details, RUNTIME.md for runtime compatibility, and PROVENANCE.md for source provenance.
