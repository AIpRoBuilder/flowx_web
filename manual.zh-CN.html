FLOWX / 手册

从克隆代码
到第一次完整构建

01 / 前置条件

你需要什么

  • Python 3.10 或更高版本。
  • Git，用于获取 FlowX 及其工作流运行时依赖。
  • 一个支持 MCP 的编码 Agent，或你自己的 Python / A2A Agent，用来编写 FlowX 请求的产物。

FlowX 不调用模型。它把每个产物的契约交给 Agent，审计并测试返回结果，发布版本化节点，渲染 FastAPI 服务并运行它。

不需要密钥：Provider 和媒体变量只在你生成的工作流调用模型或媒体服务时才需要。请放在进程环境或工作流服务自己的 .env 中。

02 / 安装

克隆并安装

一次安装包含共享核心、MCP 服务、Python SDK 和 A2A 适配器。

bash
git clone https://github.com/AIpRoBuilder/FlowX.git
cd FlowX
python3.10 -m venv .venv
source .venv/bin/activate
python -m pip install --upgrade pip
python -m pip install -e .

项目也支持 Poetry、uv 和 conda。Poetry：poetry env use python3.10 和 poetry install；uv：uv sync；conda：conda env create -f environment.yml。

03 / 配置

指定工作区

复制示例环境文件，并设置工作流和产物所在的工作区。

.env
cp .env.example .env

# .env
FLOWX_DEFAULT_WORKSPACE=./.flowx_workspaces

FLOWX_CONFIG_ROOT 可让已安装的 flowx-mcp 找到仓库外的 .env。FLOWX_EXTRA_PATHS 可在当前环境未安装 ag_ui_workflow 时指向本地源码。

SDK 和 A2A 服务读取进程环境变量，不会自动加载这个 .env。请在创建客户端前导出设置或加载文件：set -a; source .env; set +a。

04 / MCP

注册本地服务

先检查入口，再把虚拟环境中 flowx-mcp 的绝对路径注册到 MCP 客户端。

bash
flowx-mcp            # 本地 stdio 入口
flowx-mcp --verbose  # 详细日志
python3.10 run_server.py  # 源码检出入口
mcp.json
{
  "mcpServers": {
    "flowx": {
      "command": "/absolute/path/to/your/venv/bin/flowx-mcp",
      "env": {
        "FLOWX_DEFAULT_WORKSPACE": "/absolute/path/to/flowx_workspaces"
      }
    }
  }
}

MCP 主机可能不会继承 Shell 的 PATH。请使用绝对路径，并按客户端的安全建议保存工作流凭据。

05 / AGENT SKILL

教会宿主使用整个循环

FlowX skill 会引导兼容的编码 Agent 构建、检查、修复、运行和演进工作流。安装 skill 只复制指令和脚本，不包含 SDK；注册 MCP 是另一个步骤。

Claude Code

npx skills add AIpRoBuilder/FlowX --skill flowx-workflows -a claude-code -g

Codex

npx skills add AIpRoBuilder/FlowX --skill flowx-workflows -a codex -g

Hermes Agent

hermes skills install AIpRoBuilder/FlowX/skills/flowx-workflows

VS Code / Copilot

mkdir -p ~/.copilot/skills/flowx-workflows，再把 skills/flowx-workflows/. 复制进去。

DeepSeek Harness 还提供只读查看器插件，需要在 FlowX 检出目录中单独运行 dsh plugin --profile web add ./plugins/deepseek-harness-flowx 安装。构建、演进和运行工作流使用 skill。

06 / 第一次构建

描述、提交、检查

配置完成后，让支持 MCP 的 Agent 构建一个具体任务。FlowX 会分配工作流、返回契约包，并检查每个产物。

PROMPT
Use flowx to build a workflow.

Build a workflow that accepts a support ticket, classifies its
category, assigns a priority, and drafts a reply. Name the reply
node draft_reply. Return the category, priority, and draft reply
as structured output.

接下来会发生什么

  • create_workflow 分配目录和 workflow_id。
  • begin_build 打开修订，并返回每个产物的契约 next_tasks。
  • Agent 依次提交需求、图，然后为每个节点提交一对代码和测试。
  • 拒绝会返回规则、行号、修复建议和修复任务；max_attempts 有上限。
  • get_build_state 和 get_build_events 显示阶段、节点状态、下一步和日志。

构建状态保存在 MCP 服务进程和 build/events.jsonl 中。服务重启后再次调用 begin_build：已发布节点会复用，只请求未完成的工作。

07 / PYTHON SDK

嵌入构建器

当自己的 Python Agent 或应用后端需要在不使用 MCP 传输的情况下回答契约时，使用 SDK。

python
from flowx_sdk import FlowXClient

def solve(task: dict) -> dict:
    # contract、context、meta 和 submit.slots 说明要写什么。
    return my_agent.write(task)

with FlowXClient(workspace="./workflows") as flowx:
    workflow_id = flowx.create_workflow("ticket-triage")
    state = flowx.build(workflow_id, "Categorize support tickets.", solve)
    assert state["status"] == "completed", state["errors"]
    print(flowx.run_service(workflow_id))
    input("Press Enter to stop the service... ")

使用服务时保持客户端开启；退出 with 块会停止它启动的服务并中止未完成的构建，已发布版本会保留。需要更细的控制时，直接调用 begin_build、get_tasks、submit_task、get_build_state、get_build_events、reopen_stage 和 abort_build。

08 / A2A

让另一个 Agent 委托

启动非流式 A2A 适配器，让对等 Agent 连接。一次构建就是一个 A2A 任务；契约任务未完成时，任务状态为 input-required。

bash
flowx-a2a --host 127.0.0.1 --port 8001

Agent card 位于 /.well-known/agent-card.json，JSON-RPC 位于 /a2a。支持 message/send、tasks/get 和 tasks/cancel。

09 / 架构

两个实体，三种接入方式

flowx_core.builder（WorkflowBuilder）发放契约，用审计器和 pytest 验证返回结果，发布版本并渲染服务。flowx_core.service（ServiceManager）运行并驱动结果。flowx_mcp、flowx_sdk 和 flowx_a2a 把它们暴露给不同的 Agent 宿主。

仓库结构一次安装
packages/core   flowx_core   builder · service · auditors
packages/mcp    flowx_mcp    本地 stdio 服务
packages/sdk    flowx_sdk    Python 客户端
packages/a2a    flowx_a2a    非流式适配器
skills/         flowx-workflows
plugins/        DeepSeek Harness · Hermes

10 / 安全边界

运行前先审阅

  • 提交的节点测试会在本地 pytest 中运行，冒烟测试或服务运行会执行生成代码。运行服务前请审阅产物和代码。
  • 生成的代码和测试没有沙箱隔离；Provider 调用可能产生费用。
  • 工作流文件归 FlowX 所有。用 read_workflow_artifact 读取，用 begin_build 或 begin_evolve 修改；verify_workflow 会检查记录的 SHA-256 摘要。
  • 凭据放在进程环境或工作流服务自己的 .env 中；不要提交到代码仓库。
需要完整协议？ 阅读 DYNAMIC_WORKFLOW.md 了解构建器细节，RUNTIME.md 了解运行时兼容性，PROVENANCE.md 了解来源追溯。
