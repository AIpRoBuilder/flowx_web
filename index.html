02 / WHAT YOU GET

More than an answer.
Build the process

FlowX is the execution layer behind your agent: it hands out contracts, gates what comes back, and keeps only what passes

✳
01 / CONTRACTS

Contracts, not prompts

Every build step returns instructions, rules, context, and artifact slots; the host agent writes the code instead of guessing at a result

⌁
02 / GATES

Audit and test every node

Auditors and pytest gate each node; failures return findings with line, remediation, and a bounded repair task

↻
03 / VERSIONS

Publish only what passes

Accepted artifacts become versioned nodes; a failing node is not published and its descendants are blocked

⌘
04 / EVOLUTION

Evolve without rebuilding

Target a node or the whole graph; unchanged nodes are reused, and the workflow keeps its history

03 / HOW IT WORKS

Nine steps.
One inspectable build

From any harness to a versioned service: every step leaves an artifact, a gate result, or a journal entry you can read

STEP 01

Any harness

STEP 02

Describe the intent

Tell your agent what the workflow should do. The agent allocates a workflow and opens a build revision; FlowX chooses the stages and opens the first contracts.

NATURAL LANGUAGECREATE_WORKFLOWBEGIN_BUILD
INTENTAGENT
› Use flowx to build a workflow.

  A support ticket comes in. Classify its category,
  assign a priority, and draft a reply as
  structured output.

create_workflow(name="ticket-triage")
→ workflow_id: ticket-triage
STEP 03

Receive a contract

begin_build returns next_tasks: a contract for each artifact with instructions, rules, schema, context, and the slots to submit. The agent does not have to guess the shape.

CONTRACTSCHEMAARTIFACT SLOTS
NEXT_TASKSREQUIREMENT
{
  "task": "requirement",
  "contract": { "rules": [...], "schema": {...} },
  "context": {},
  "submit": { "slots": ["requirement"] }
}
STEP 04

Write the artifacts

Your coding agent writes the requirement, then the graph, then one code and test pair per node. Independent nodes are open at the same time.

REQUIREMENTGRAPHCODE + TEST
WORKSPACETICKET-TRIAGE
workflows/ticket-triage/
├── requirement.md
├── workflow.json
├── nodes/
│   ├── classify.py      + test_classify.py
│   ├── prioritize.py    + test_prioritize.py
│   └── draft_reply.py   + test_draft_reply.py
└── build/events.jsonl
STEP 05

Audit what came back

FlowX runs its auditors against every artifact. A rejection is specific: rule, message, line, and remediation, so the agent can fix exactly what failed.

DETERMINISTIC RULESFINDINGSREMEDIATION
AUDITFINDINGS
AUDIT  graph        PASS
AUDIT  classify     FAIL
  rule_id:  node.schema-output
  line:     42
  message:  "category" is not validated
  remediation:
    validate the field against the declared enum
STEP 06

Test under pytest

Each node's test runs locally. Failures come back as a repair task with the test output; repair attempts are bounded, so a build cannot loop forever.

PYTESTREPAIR TASKMAX_ATTEMPTS
PYTESTNODE: CLASSIFY
$ pytest nodes/test_classify.py
FAILED test_classify_rejects_unknown_category
1 failed, 4 passed

→ repair task opened (attempt 2 / 3)
STEP 07

Publish versions

Accepted nodes are published with versions. A node that still fails is not published, and its descendants are marked blocked. get_build_state and the journal show exactly where the build stands.

VERSIONED NODESBUILD STATEJOURNAL
GET_BUILD_STATEBUILDING
status: building
nodes:
  classify      published v2
  prioritize    published v1
  draft_reply   repair (attempt 2/3)
entrypoint: waiting
STEP 08

Run the service

run_service renders and starts the FastAPI backend. run_step feeds input, reset_session clears a paused run, and get_evidence returns the journal plus the service log tail.

FASTAPIRUN_STEPEVIDENCE
SERVICERUNNING
run_service("ticket-triage")
  http://127.0.0.1:8000

run_step("ticket-triage", "classify", {...})
  completed · 3 cards
get_evidence("ticket-triage")
  runs/latest.json + service.log
STEP 09

Evolve and reuse

begin_evolve changes one node with the topology frozen, or the whole graph. Everything whose inputs did not change is reused; published versions stay available.

BEGIN_EVOLVENODE OR GRAPHREUSE
EVOLVEDRAFT_REPLY
begin_evolve("ticket-triage",
  intent="Escalate urgent tickets",
  scope="node", node="draft_reply")

reused    classify v2, prioritize v1
rewritten draft_reply v2
published draft_reply v2

04 / QUICKSTART

Install locally.
Build your first workflow

FlowX runs on Python 3.10+ and needs no model key. Install it, connect over MCP or the SDK, and let your agent write the artifacts

macOS / LINUX · PIP
git clone https://github.com/AIpRoBuilder/FlowX.git
cd FlowX
python3.10 -m venv .venv
source .venv/bin/activate
python -m pip install --upgrade pip
python -m pip install -e .

No model key is needed inside FlowX; provider and media variables are only for the workflows you generate. On Windows, activate .venv\Scripts\activate and use the Scripts executables.

01 / MCP

Connect your agent

Register the local stdio server in your MCP client; use absolute paths because MCP hosts may not inherit your shell's PATH

mcp.json
{
  "mcpServers": {
    "flowx": {
      "command": "/absolute/path/to/venv/bin/flowx-mcp",
      "env": {
        "FLOWX_DEFAULT_WORKSPACE": "/absolute/path/to/flowx_workspaces"
      }
    }
  }
}

FLOWX_CONFIG_ROOT lets an installed flowx-mcp find a .env outside the checkout. Keep workflow credentials in the process environment or the service's own .env; never commit secrets

02 / PYTHON SDK

Build a workflow in code

FlowXClient exposes the same protocol; build() answers every contract task with a function you provide

build_workflow.py
from flowx_sdk import FlowXClient

def solve(task: dict) -> dict:
    return my_agent.write(task)

with FlowXClient(workspace="./workflows") as flowx:
    workflow_id = flowx.create_workflow("ticket-triage")
    state = flowx.build(
        workflow_id,
        "Categorize and prioritize support tickets.",
        solve,
    )
    assert state["status"] == "completed", state["errors"]
    print(flowx.run_service(workflow_id))

Node tests execute locally while you build, so review the generated code before running the service. Keep the client open while using a started service

08 / GOOD TO KNOW

Questions

Want to know more about FlowX?

Read the full manual ↗
Is FlowX a visual workflow editor?+

No; FlowX is a workflow builder and service manager without a built-in interface. Your agent or application handles interaction and presentation, while FlowX builds, gates, versions, and runs the process behind it

Does FlowX call a model?+

No. FlowX has no LLM inside. It hands your coding agent a contract for each artifact and audits what comes back; provider keys are only needed by workflows you generate that call a model or media service

Where are generated workflows stored?+

Workflow artifacts live under workspace/workflows/<workflow_id>, including the requirement, workflow graph, versioned node code and tests, the entrypoint, and the build journal

What happens when a node fails its test?+

Auditors and pytest return findings with line, remediation, and a repair task; repair attempts are bounded. A node that still fails is not published, and its descendants are blocked

How can I connect to FlowX?+

FlowX supports local stdio MCP, a Python SDK, an A2A adapter, and an agent skill for Claude Code, Codex, and Hermes Agent; DeepSeek Harness also has a read-only viewer plugin. The A2A adapter currently supports non-streaming workflow building.
