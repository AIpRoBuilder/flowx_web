FLOWX / WHY FLOWX

Contracts, not prompts.
Process, not a one-off answer.

An agent can produce a plausible answer in one turn. A team needs the same result every time, with a graph, tests, versions, and evidence. FlowX exists to make the second one possible.

01 / THE PROBLEM

If the model owns the control flow,
the process is a guess

Prompt-driven systems re-decide what to do on every run. That is flexible in a demo and fragile in production

AGENT-CENTRIC BY DEFAULT

The answer is the artifact

The model decides the next step, gathers context, and returns a result. Nothing outside the conversation records why it worked.

  • The control flow is probabilistic on every run
  • Context and tool results are re-read and re-reasoned each time
  • A fix often means rebuilding the whole behavior
  • There is no graph, test suite, version, or run journal to inspect
CONTRACT-CENTRIC WITH FLOWX

The process is the artifact

Your coding agent writes at build time. FlowX defines the artifact, gates the result, and runs deterministic code afterwards.

  • One contract per artifact: requirement, graph, node code and test
  • Auditors and pytest decide what is published
  • Failed nodes return findings and a bounded repair task
  • Changes reuse nodes whose inputs did not change

02 / WHAT YOU GET

Six guarantees
behind every build

These are properties of the builder and service manager, not conventions your team has to remember

01 / CONTRACT

One artifact at a time

Each task carries its instructions, rules, schema, context, and submission slots. The host agent never has to guess the shape.

02 / AUDIT

Findings, not vibes

A rejection names the rule, message, line, and remediation, so the next attempt can fix exactly what failed.

03 / TEST

pytest in the loop

Node tests run locally while you build. Repair attempts are bounded; a build cannot spin forever.

04 / VERSION

Only passing work ships

Accepted artifacts become versioned nodes. A failing node is not published, and its descendants are blocked.

05 / EVIDENCE

Run journal and logs

get_evidence returns the latest run journal and service log tail for the next fix.

06 / REUSE

Evolve one node

begin_evolve can rewrite a node with the topology frozen, or the whole graph; unchanged nodes are reused.

03 / THE BUILD

Everything leaves a trace

FlowX does not ask you to trust a transcript. The build writes a requirement, a workflow graph, one code and test pair per node, and a rendered entrypoint. Each artifact passes its own gate; when a gate rejects something, the finding points at the exact line and the task comes back with a remediation.

The generated service is regular FastAPI code on top of the ag_ui_workflow runtime. The service manager starts it, feeds one step at a time, resets paused sessions, and returns evidence. The intelligent UI stays above; FlowX stays underneath.
