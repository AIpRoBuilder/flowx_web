FLOWX / WHY FLOWX

Let the model reason.
Give the work a structure.

AI agents are flexible at understanding intent and choosing what to do. Repeated work also needs explicit steps, clear contracts, tests, versions, and evidence. FlowX helps your agent turn a natural-language goal into an executable process it can inspect, reuse, and evolve.

01 / THE REASON

A good answer is not
the same as a reliable process

An LLM can plan, call tools, and complete a task in one conversation. But when a task repeats, the useful part is not only the last answer — it is the method that produced it: the steps, dependencies, checks, and decisions worth keeping.

WHEN THE PROCESS LIVES ONLY IN A CONVERSATION

The method stays in the transcript

The agent may reconstruct a plan on the next run. That flexibility is useful for exploration, but the method can be difficult to inspect, test, compare, and maintain.

  • Steps and control flow can vary between runs
  • A useful fix may be buried in a transcript
  • It can be hard to tell which part changed or why
  • There may be no versioned artifact or test evidence
WITH FLOWX, THE PROCESS BECOMES AN ARTIFACT

The method becomes the artifact

Your host agent still reasons and writes the workflow. FlowX supplies contracts, checks the returned artifacts, publishes passing versions, and runs the resulting service.

  • Requirements, graph, node code, and tests are explicit
  • Auditors and pytest gate what gets published
  • Failures return findings and bounded repair tasks
  • Targeted changes can reuse unaffected nodes

02 / WORK HAS A SHAPE

Language expresses intent.
Work changes state

Think about painting a landscape. The goal fits in one sentence, but the work is organized through stages, materials, operations, and visual feedback. The artist does not calculate every pixel from scratch; they use learned techniques and a working process.

STAGE 01

Compose

Set the structure, proportions, and intended focal point.

STAGE 02

Block in

Establish large color areas before refining small details.

STAGE 03

Layer & refine

Apply techniques in context; adjust light, depth, and form.

STAGE 04

Review & amend

Inspect the result, identify what is off, and revise the right part.

✦

The point is not that every task has one fixed sequence. Good work is often conditional and iterative. FlowX makes the chosen procedure explicit enough to inspect, test, execute, and change — while the host agent remains free to reason about the goal and the next improvement.

↻ FEEDBACK CAN OPEN A TARGETED WORKFLOW EVOLUTIONEVIDENCE AT EVERY STAGE

FlowX does not ask you to trust a transcript. The build writes a requirement, a workflow graph, one code and test pair per node, and a rendered entrypoint. Each artifact passes its own gate; when a gate rejects something, the finding points at the exact line and the task comes back with a remediation.

The generated service is regular FastAPI code on top of the ag_ui_workflow runtime. The service manager starts it, feeds one step at a time, resets paused sessions, and returns evidence. The intelligent UI stays above; FlowX stays underneath.

05 / WHAT YOU GET

Six guarantees
behind every build

These are properties of the builder and service manager — not reminders your team has to keep in its prompt.

01 / CONTRACT

One artifact at a time

Each task carries its instructions, rules, schema, context, and submission slots. The host agent never has to guess the shape.

02 / AUDIT

Findings, not vibes

A rejection names the rule, message, line, and remediation, so the next attempt can fix exactly what failed.

03 / TEST

pytest in the loop

Node tests run locally while you build. Repair attempts are bounded; a build cannot spin forever.

04 / VERSION

Only passing work ships

Accepted artifacts become versioned nodes. A failing node is not published, and its descendants are blocked.

05 / EVIDENCE

Run journal and logs

get_evidence returns the latest run journal and service log tail for the next fix.

06 / REUSE

Evolve one node

begin_evolve can rewrite a node with the topology frozen, or the whole graph; unchanged nodes are reused.

07 / FIT & BOUNDARIES

Bring your agent.
Keep your way of working

FlowX is designed to sit underneath an existing agent host. It does not replace the model's reasoning or require FlowX to own model credentials.

Where FlowX fits

The same builder and service manager are exposed through three interfaces, so different hosts can operate the same workflow artifacts.

  • Local stdio MCP server
  • Python SDK for agents and applications
  • A2A adapter for peer-agent interaction
  • Agent hosts such as Claude Code, Codex, Hermes, and DeepSeek Harness

What FlowX does not claim

Explicit workflows complement flexible reasoning; they do not make every task deterministic or remove the need for judgment.

  • FlowX is not another general-purpose LLM or agent.
  • It does not automatically turn every conversation into a skill.
  • Model calls and external services can still be probabilistic or fail.
  • Its current service manager is not a claim of Temporal-style distributed crash recovery.
Clear division of responsibility: the host agent interprets and authors; FlowX contracts, audits, tests, versions, and runs the workflow. The process becomes a managed artifact without taking reasoning away from the agent.
