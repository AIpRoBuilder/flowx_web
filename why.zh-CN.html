FLOWX / 为什么是 FLOWX

让模型去推理。
给工作一个结构。

AI Agent 擅长理解意图、选择做法。但重复性的工作还需要明确的步骤、清晰的契约、测试、版本和证据。FlowX 帮助你的 Agent 把自然语言目标变成可检查、可复用、可持续演进的可执行流程。

01 / 原因

好的回答，
不等于可靠的流程

LLM 可以在一次对话里完成规划、调用工具并交付任务。但当任务重复出现时，真正有价值的并不只是最后一次回答，而是产生它的方法：值得保留的步骤、依赖、检查和决策。

流程只存在于对话里

方法留在对话记录中

Agent 下次运行时会重新构建计划。这种灵活性适合探索，但方法本身却难以检查、测试、比较和维护。

  • 步骤和控制流在不同运行之间可能变化
  • 一次有效的修复可能埋没在对话记录里
  • 很难看出哪一部分变了、为什么变
  • 没有可用的版本化产物或测试证据
在 FLOWX 中，流程成为产物

方法本身成为产物

宿主 Agent 仍然负责推理和编写工作流。FlowX 提供契约、检查返回的产物、发布通过的版本，并运行生成的服务。

  • 需求、图、节点代码和测试都是显式的
  • 审计器和 pytest 决定什么可以发布
  • 失败会返回检查结果和有限范围的修复任务
  • 定向修改可以复用未受影响的节点

02 / 工作有其形状

语言表达意图。
工作改变状态

想象画一幅风景画。目标可以用一句话表达，但工作要通过阶段、材料、操作和视觉反馈来组织。画家不需要从零计算每一个像素，而是使用学到的技法和一套工作过程。

STAGE 01

构图

确定结构、比例和想要强调的视觉焦点。

STAGE 02

铺色

先建立大的色块，再细化小的细节。

STAGE 03

叠加与细化

在语境中运用技法，调整光线、深度和形体。

STAGE 04

审视与修改

检查结果，找出问题所在，并修改对应的部分。

✦

重点不是每个任务都只有一种固定顺序。好的工作往往是条件性的、迭代的。FlowX 把选定的过程明确到足以检查、测试、执行和修改，同时让宿主 Agent 继续自由地推理目标和下一次改进。

FlowX 不要求你相信一段对话记录。构建会写出需求、工作流图、每个节点一份代码与测试，以及渲染后的入口文件。每个产物都要通过自己的检查；拒绝会精确指向行号，并带着修复建议返回任务。

生成的服务是建立在 ag_ui_workflow 运行时上的普通 FastAPI 代码。服务管理器负责启动、逐步输入、清理暂停的会话并返回证据。智能 UI 留在上层，FlowX 留在下层。

  → main.py (rendered)
  → FastAPI service

gates

  entrypoint audit
  optional smoke run

05 / 你得到什么

每次构建背后的
六个保证

这些是构建器和服务管理器的属性，不是团队需要写进提示词的提醒。

01 / 契约

一次一个产物

每个任务都带有指令、规则、schema、上下文和提交槽位，宿主 Agent 不需要猜结构。

02 / 审计

检查结果，而非感觉

拒绝会给出规则、消息、行号和修复建议，下一次尝试可以只修复真正失败的部分。

03 / 测试

构建过程中跑 pytest

节点测试在本地运行，修复次数有上限，构建不会无限循环。

04 / 版本

只发布通过的内容

通过的产物成为版本化节点；失败节点不会发布，其下游节点被阻塞。

05 / 证据

运行日志和服务日志

get_evidence 返回最近的运行日志和服务日志尾部，供下一次修复使用。

06 / 复用

只演进一个节点

begin_evolve 可以在冻结拓扑的情况下重写一个节点，也可以修改整张图；未变化的节点全部复用。

07 / 适用与边界

带上你的 Agent。
保留你的工作方式

FlowX 被设计为位于现有 Agent 宿主之下。它不取代模型的推理，也不要求 FlowX 持有模型凭证。

FlowX 适配在哪里

同一个构建器和服务管理器通过三种接口暴露，不同的宿主可以操作同一批工作流产物。

  • 本地 stdio MCP 服务
  • 面向 Agent 和应用的 Python SDK
  • 用于对等 Agent 交互的 A2A 适配器
  • Claude Code、Codex、Hermes、DeepSeek Harness 等 Agent 宿主

FlowX 不声称什么

显式工作流补充灵活推理，但不会让每个任务都变成确定性的，也不会消除判断的必要。

  • FlowX 不是另一个通用 LLM 或 Agent。
  • 它不会自动把每次对话变成技能。
  • 模型调用和外部服务仍可能具有概率性或失败。
  • 当前的服务管理器并不声称具备 Temporal 式的分布式崩溃恢复能力。
清晰的职责划分：宿主 Agent 负责解释和编写；FlowX 负责契约、审计、测试、版本和运行。流程成为受管理的产物，而推理仍然属于 Agent。
