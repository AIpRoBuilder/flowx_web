FLOWX / 为什么是 FLOWX

契约，而非提示词。
流程，而非一次性回答。

Agent 可以在一轮对话里给出看似合理的回答。团队需要的是每次都得到同样的结果，并且有图、测试、版本和证据。FlowX 存在的意义，就是让后者成为可能。

01 / 问题

如果模型掌握控制流，
流程就只是猜测

提示词驱动的系统每次运行都会重新决定下一步。演示时很灵活，生产环境里很脆弱

默认的 AGENT 中心设计

回答就是产物

模型决定下一步、收集上下文并返回结果。对话之外没有东西记录它为什么成功。

  • 每次运行的控制流都是概率性的
  • 上下文和工具结果每次都要重新读取、重新推理
  • 修一个问题往往要重建整个行为
  • 没有图、测试集、版本或运行日志可供检查
FLOWX 的契约中心设计

流程就是产物

编码 Agent 在构建时编写，FlowX 定义产物、检查结果，之后运行确定性代码。

  • 每个产物一份契约：需求、图、节点代码与测试
  • 审计器和 pytest 决定什么可以发布
  • 失败节点返回检查结果和有限次数的修复任务
  • 输入未变化的节点在演进时直接复用

02 / 你得到什么

每次构建背后的
六个保证

这些是构建器和服务管理器的属性，不是团队需要记住的约定

01 / 契约

一次一个产物

每个任务都带有指令、规则、schema、上下文和提交槽位，宿主 Agent 不需要猜结构。

02 / 审计

检查结果，而非感觉

拒绝会给出规则、消息、行号和修复建议，下一次尝试可以只修复真正失败的部分。

03 / 测试

构建过程中跑 pytest

节点测试在本地运行，修复次数有上限，构建不会无限循环。

04 / 版本

只发布通过的内容

通过的产物成为版本化节点；失败节点不会发布，其下游节点被阻塞。

05 / 证据

运行日志和服务日志

get_evidence 返回最近的运行日志和服务日志尾部，供下一次修复使用。

06 / 复用

只演进一个节点

begin_evolve 可以在冻结拓扑的情况下重写一个节点，也可以修改整张图；未变化的节点全部复用。

03 / 构建

所有东西都会留下痕迹

FlowX 不要求你相信一段对话记录。构建会写出需求、工作流图、每个节点一份代码与测试，以及渲染后的入口文件。每个产物都要通过自己的检查；拒绝会精确指向行号，并带着修复建议返回任务。

生成的服务是建立在 ag_ui_workflow 运行时上的普通 FastAPI 代码。服务管理器负责启动、逐步输入、清理暂停的会话并返回证据。智能 UI 留在上层，FlowX 留在下层。

产物流只读视图
intent
  → requirement.md
  → workflow.json
  → nodes/*.py + tests
  → main.py (rendered)

gates
  requirement check
  graph audit
  node audit + pytest
  entrypoint audit
  optional smoke run

04 / 架构

两个实体。
三种接入方式

同一个构建器和服务管理器可以暴露给不同的 Agent 宿主，而工作流本身不变

01 / 构建器◇

WorkflowBuilder

发放契约，用审计器和 pytest 验证产物，发布版本，并渲染 FastAPI 服务。

构建 + 检查
02 / 服务▷

ServiceManager

运行渲染后的服务，驱动步骤，重置会话，并返回运行日志和服务日志作为证据。

运行 + 观察
03 / 宿主⇄

MCP · SDK · A2A

Claude Code、Codex、Hermes、DeepSeek Harness、Python 应用或另一个 Agent 都可以操作同样的两个实体。

带上你的 AGENT
